Manual test cases

However you try, sometimes it is not possible to fit all the testing into its automatic counterpart. To deal with this persistent issue, we had to implement some automatic testing. The problem is that not all requirements in the game are quantitative or objectively measurable, so we have to involve a potential user (or in some cases one of the members of our team) who can check whether the rest of the game works in an intended manner. In some cases, however, we just simply couldn't automate the tests as some of the functionality of the game is not isolatable from its enterity. And what do we mean by that, is that, for example, the map with all of its obstacles could not be tested automatically. For that we had to draw out additional tests to check whether it functions in an intended matter.

In UniSim, the following parts of the game could not be tested using unit or integration testing:

  • Whether a map exists and displayed correctly,
  • Whether obstacles on the map exist and are behaving in an intended manner,
  • Whether the user interface is clear and easy to understand,
  • Whether all the interactive elements of the UI work and give a clear indication of that.

To deal with each of those requirements, we have grouped them by the purpose they serve — to test the map and to test the game UI. It might already become clear to the reader that this will results in 2 test case scenarios that has to be gone through. They are described below.

Scenario 1

The following scenario describes the steps to be taken to test the functionality of the map. Follow it exactly and stop to note any deviation from the expected results that are described below each of the steps. This scenario tests the following requirements: FR_MAP, FR_OBSTACLES, FR_MAP_ROADS, and FR_BUILDING_SPACE.

  1. Instruction: Press Play button.

    Expected outcome: Start screen changes to Game screen with the visible map

  2. Instruction: Try dragging the map in all 4 directions by holding left click.

    Expected outcome: The screen should change to the location you dragged on the map

  3. Instruction: Try zooming in and out by scrolling the mousewheel

    Expected outcome: The map should resize

  4. Instruction: Inspect the map for obstacles

    Expected outcome: The map should have a river

  5. Instruction: From a selection of buildings, select a building and try to place it over a river

    Expected outcome: The building won't be placed

  6. Instruction: Inspect the map for roads

    Expected outcome: The map should have roads

  7. Instruction: From a selection of buildings, select a building and try to place it over a road

    Expected outcome: The building won't be placed

  8. Instruction: From a selection of buildings, select each building and place them in an obstacle free area next to each other

    Expected outcome: The building take up map space relative to their size; i.e. a library takes up more tiles on the map than the bakery would do

Scenario 2

The following scenario describes the steps to be taken to test the functionality of the map. Follow it exactly and stop to note any deviation from the expected results that are described below each of the steps. This scenario tests the following requirements: FR_USER_INTERFACE, FR_INTERACTIVE_ELEMENTS, FR_SATISFACTION_BAR, FR_PAUSE_GAME, FR_UNPAUSE_GAME.

  1. Instruction: Press Settings.

    Expected outcome: Start screen changes to settings menu.

  2. Instruction: Drag the volume back and forth.

    Expected outcome: The volume level changes in accordance with the position of the scroller.

  3. Instruction: Press Back button.

    Expected outcome: The settings menu goes back to the start screen.

  4. Instruction: Press Play button.

    Expected outcome: Start screen changes to Game screen with the visible map

  5. Instruction: Check whether the lower part of the UI has all the placeable buildings. A rule of thumb: there must be at least five.

    Expected outcome: The lower part of the UI (building menu) has all the buildings that can be placed

  6. Instruction: For each of the available buildings, select it and try to place it down.

    Expected outcome: The button is clicked and allows the user to put down a building.

  7. Instruction: Check whether current time is clear and visible in the upper part of the UI

    Expected outcome: Current time is clear and visible in the upper part of the UI

  8. Instruction: Press the pause button

    Expected outcome: The game state freezes, no buildings can be placed, and the timer stops.

  9. Instruction: Press the unpause button

    Expected outcome: The game state resumes, buildings can be placed once again, and the timer continues to run.

  10. Instruction: Check whether satisfaction score is clear and visible in the upper part of the UI

    Expected outcome: Satisfaction score is clear and visible in the upper part of the UI
